# Lab 4 — Security and code quality

**20 minutes.** Outcome: findings triaged and remediated through the normal pull
request flow.

This repository contains a deliberate, documented weakness so the scan finds something
real. Do not go looking for it before the scan runs — the point is to practise the
triage workflow, not to play spot-the-bug.

## 1. Enable code scanning

1. **Settings → Advanced Security** (under *Security and quality* in the sidebar).
2. Next to **CodeQL analysis**, choose **Set up → Default**.
3. Review the detected languages, then **Enable CodeQL**.

Default setup builds the configuration for you and triggers the first analysis. GitHub
Actions must be enabled on the repository for this to work.

## 2. Read the alert before you fix anything

Open the **Security** tab → **Code scanning**. Expect a finding in the parts module.

Read, in this order:

- the rule name and the class of weakness it describes,
- the data flow the analysis traced, from the request value to where it is used,
- the affected line in `src/modules/parts/routes.ts`.

Then ask Copilot to ground it in this codebase:

```text
Explain this code scanning alert in the context of #file:src/modules/parts/routes.ts.
Which request value reaches which sink, and what could an attacker actually achieve
against a warehouse terminal? Then tell me which rule in
.github/copilot-instructions.md this violates.
```

The answer should point at the rule: *never render a request value into an HTML string*.

## 3. Reproduce it yourself

An alert you have not seen fire is an alert you will not take seriously:

```bash
curl -s -H "Authorization: Bearer aoph_viewer_workshop_key" \
  "http://localhost:3000/api/parts/label?sku=AOP-BRK-1001&operator=%3Cscript%3Ealert(1)%3C%2Fscript%3E"
```

The script tag comes straight back inside the HTML.

Now contrast it with the rest of the application. Open the dashboard, create a part
named `<script>alert(1)</script>`, and look at the table. It renders as literal text,
because `app.js` sets `textContent` and never `innerHTML`. Same data, same request path
— different sink, different outcome. That contrast is the lesson.

## 4. Generate a fix

On the alert, use **Generate fix** (Copilot Autofix). Read the suggested change and its
explanation.

## 5. Review it — this is the part that matters

Run the four questions from the deck:

1. Does this actually remove the weakness, or only move it?
2. Does the change alter behaviour the application depends on?
3. Are the existing tests still meaningful after this change?
4. Would I approve this from a colleague?

Autofix suggestions are generated by an AI model and are not guaranteed to be correct,
complete or secure. Review, validate and test before merging.

**Push the discussion further than escaping.** Escaping the two parameters makes the
alert go away. But the repository standard says this endpoint should not be building
HTML from request input at all — the rest of the application already proves the
alternative works. Which fix would you actually merge: the one that silences the
scanner, or the one that satisfies the standard? Decide as a group, and justify it.

## 6. Add the regression test

A fix without a test is a fix that comes back:

```text
Add a test to tests/api.test.ts proving the label endpoint does not reflect raw
request input into its response. Follow
#file:.github/instructions/tests.instructions.md.
```

## 7. Merge through the normal flow

Open the pull request, let CI run, get a review, merge. The security fix takes exactly
the same path as a feature. That is the point.

## Checkpoint

- [ ] Code scanning enabled and at least one analysis completed
- [ ] You reproduced the weakness with curl, and saw the dashboard handle the same
      input safely
- [ ] One finding remediated, with a regression test, and validated by you
- [ ] You can state in one sentence why the original code was unsafe

## Stretch goal

Run the review prompt file across the module you built in Lab 2:

```text
/review-api-security module=src/modules/stock-requests
```

Compare its findings against what CodeQL reported. They catch different things — CodeQL
traces data flow, the prompt file checks your own domain rules about transactions,
roles, audit coverage and whether the dashboard duplicated a validation rule.
