# Specification — Stock request module (Lab 2)

A workshop technician raises a **stock request** to draw parts from a warehouse for a
repair job. A warehouse operator approves or rejects it. Approval reduces stock.

This is the context you attach in Lab 2. Do not implement it by hand — attach it to
Copilot in Agent mode with `#file:docs/spec-stock-requests.md`.

## Why this module and not another CRUD table

It deliberately touches every pattern in the codebase at once: validation, a state
machine, a cross-entity check, a transaction, optimistic concurrency, role-based
authorisation, the audit trail, and a dashboard tab with its own forms. If the agent
gets all of them right, it has genuinely followed the repository standards rather than
produced generic code.

## Domain

| Field | Type | Rules |
|---|---|---|
| `id` | string | UUID, generated by the service |
| `reference` | string | `SR-YYYY-NNNN`, sequential per calendar year, like purchase orders |
| `partId` | string | Must reference an existing, active part |
| `quantity` | integer | Greater than 0, at most 500 |
| `requestedBy` | string | 1–120 characters |
| `jobReference` | string \| null | Optional workshop job number, at most 40 characters |
| `status` | enum | `pending`, `approved`, `rejected`, `cancelled` |
| `note` | string \| null | Optional, at most 240 characters |
| `decidedBy` | string \| null | Set when the request leaves `pending` |
| `version` | integer | Starts at 1, incremented on every change |
| `createdAt` | string | ISO 8601 UTC |
| `decidedAt` | string \| null | Set when the request leaves `pending` |

## State machine

Follow the `ALLOWED_TRANSITIONS` pattern from the purchase-orders module — a map, not
a chain of `if` statements — and expose it at
`GET /api/stock-requests/transitions` so the dashboard can read it.

```
pending   -> approved | rejected | cancelled
approved  -> (terminal)
rejected  -> (terminal)
cancelled -> (terminal)
```

## Business rules

1. A request for an unknown or inactive `partId` is rejected with **400**, with the
   field named in `error.details`.
2. A request whose `quantity` exceeds the part's current `stockQuantity` is rejected
   with **409** and the code `insufficient_stock`.
3. Approval re-checks availability at approval time, not only at creation time — stock
   may have moved in between. If it is no longer available, return **409**.
4. Approval decrements the part's `stockQuantity` by the requested quantity. The status
   change and the stock decrement happen in **one transaction**: either both succeed or
   neither does.
5. A request that is no longer `pending` cannot be decided again — respond **409** with
   the code `already_resolved`.
6. Only the person named in `requestedBy` may cancel their own pending request. Anyone
   else attempting it gets **403**.
7. Approving or rejecting requires the `operator` role. Raising a request requires
   `operator`. Reading requires `viewer`.
8. Every transition records an audit event: `stock_request.created`,
   `stock_request.approved`, `stock_request.rejected`, `stock_request.cancelled`.

## Endpoints

| Method | Path | Role | Behaviour |
|---|---|---|---|
| `GET` | `/api/stock-requests` | viewer | List with `status`, `partId`, `requestedBy`, plus the standard `limit`, `offset`, `sort`, `direction`. Returns `{ items, total, limit, offset }`. |
| `GET` | `/api/stock-requests/transitions` | viewer | The allowed state transitions. |
| `GET` | `/api/stock-requests/:id` | viewer | A single request, or 404. |
| `POST` | `/api/stock-requests` | operator | Create. Returns **201**. |
| `POST` | `/api/stock-requests/:id/approve` | operator | Approve and decrement stock. Returns **200**. |
| `POST` | `/api/stock-requests/:id/reject` | operator | Reject with a reason in the body. Returns **200**. |
| `POST` | `/api/stock-requests/:id/cancel` | operator | Cancel your own pending request. Returns **200**. |

Sortable fields: `reference`, `createdAt`, `quantity`, `status`.

## Schema addition

Add to `src/db/schema.sql`, keeping the migration idempotent:

```sql
CREATE TABLE IF NOT EXISTS stock_requests (
  id            TEXT PRIMARY KEY,
  reference     TEXT NOT NULL UNIQUE,
  part_id       TEXT NOT NULL REFERENCES parts (id) ON DELETE RESTRICT,
  quantity      INTEGER NOT NULL CHECK (quantity > 0 AND quantity <= 500),
  requested_by  TEXT NOT NULL,
  job_reference TEXT,
  status        TEXT NOT NULL CHECK (status IN ('pending', 'approved', 'rejected', 'cancelled')),
  note          TEXT,
  decided_by    TEXT,
  version       INTEGER NOT NULL DEFAULT 1,
  created_at    TEXT NOT NULL,
  decided_at    TEXT
);

CREATE INDEX IF NOT EXISTS idx_stock_requests_status ON stock_requests (status);
CREATE INDEX IF NOT EXISTS idx_stock_requests_part ON stock_requests (part_id);
```

## Dashboard

Add a **Stock requests** tab, following `.github/instructions/frontend.instructions.md`.
The placeholder comment in `public/index.html` marks where the tab goes.

It needs:

- a view config in `public/app.js` with columns for reference, part, quantity,
  requested by, status badge and created date,
- a **New request** form with a part picker (from `/api/parts/options`), a quantity,
  a requester and an optional job reference,
- row actions for Approve, Reject and Cancel that appear only when the transition map
  allows them and `me.can.write` is true,
- the entity added to `public/api-client.js`.

Remember: no validation logic in the client, no `innerHTML`, and read the transitions
from the API rather than hard-coding them.
